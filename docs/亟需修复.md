## P1-02 部署不可追溯、非原子，还会删除备份凭据

### 已确认事实

- `deploy.sh:10-15` 只检查已跟踪 diff，并使用 `git add -u`；新文件不会进入提交。
- `deploy.sh:19-25` 随后从当前工作树执行 `rsync --delete-after`，所以未提交/未跟踪文件仍会进入生产，GitHub commit 与线上内容可能不同。
- `deploy/r2-setup.sh:6-8` 默认把生产专用配置放在 `/opt/vocabflow/.rclone.conf`；它不在本地源，也没有被 rsync exclude，部署会将其作为“目标端多余文件”删除。
- `deploy/update-native.sh:9-14` 先备份、原地升级 live venv、导入应用，最后才执行需要密码的 `sudo systemctl restart`。
- 当前非交互环境已经实际发生 sudo 失败：文件/依赖已改变，但旧进程继续运行；下次重启才会突然加载新代码。

### 影响

- 配置好的异地备份可被下一次发布静默关闭，只留下 `R2_SKIP` 日志。
- 旧 Python 进程可能读取新模板/静态资源或已被部分修改的 venv，形成前后端混合版本。
- 无法证明服务器对应哪个 commit，也无法在健康失败时自动回滚到一个完整版本。

### 最小修复

1. 立即将 R2 配置移到 root-only 的 `/etc/vocabflow/rclone.conf`；发布同步永远不碰密钥目录。
2. 发布前要求工作区干净、目标 commit 已 push；从确定 SHA 的 `git archive`/发布产物构建 staging，而不是 rsync 工作树。
3. 在任何线上写入前执行最小权限 `sudo -n` 重启预检；只授权目标 service 的 restart。
4. 使用版本化 release 目录和独立 venv，验证 import/migration 后原子切换 `current`，再重启。
5. 健康/版本不匹配时自动切回旧 release；写入 `REVISION` 并由 readiness 暴露。

### 验收标准

- 在测试目标放置仅目标端存在的 `.rclone.conf`，rsync dry-run 不会删除或覆盖它。
- 未跟踪应用文件、未 push commit、sudo 不可用时，部署在改写线上任何内容前失败。
- 注入 rsync/pip/import/restart/health 任一失败，旧 release、旧 venv 和旧进程保持一致可用。
- 成功部署后 `REVISION == git rev-parse HEAD`，服务返回预期版本。

## P1-03 Anki 多模板 note 会静默丢卡和复习历史

### 触发条件与证据

- Anki 的一个 note 可用多个模板生成多张 card，例如 Basic+Reverse 或包含多个 Cloze ordinal。
- `app/anki_exchange.py:290-340` 将每张 card 的身份解析为 `note_guid:ordinal`，这是正确方向。
- 但 `app/models.py:273-276` 同时限制 `(user_id, word, card_type)` 唯一。
- `app/anki_exchange.py:390-404` 找不到 GUID 时又按“用户 + word + card_type”找 candidate；第二张卡与第一张 word/type 相同、GUID 不同时直接计为 conflict。
- 该卡对应的 revlog 也不会导入。现有 round-trip 测试只有单 note/单 ordinal，没有覆盖此场景。

### 影响

- 导入响应可能只显示“跳过冲突”，用户却不知道缺的是哪个模板和多少历史。
- 从 Anki 迁移到 VocabTool 后，反向卡、Cloze 多卡和对应学习进度可能永久缺失。

### 最小修复

- 以 `(user_id, note_guid, ordinal)` 或等价稳定 card identity 为 Anki 卡唯一身份。
- 允许同一用户、同一词、同一 `card_type=anki` 有多个外部卡；站内生成卡的去重规则与外部 Anki 身份分开。
- 同时保存/解释模板 ordinal，确保反向模板的 front/back 语义正确，而不只是放开唯一约束。
- 数据库改动只新增版本化迁移；上线前在数据库副本验证唯一约束变化，不直接重写生产卡片。

### 验收标准

- fixture：1 个 note、2 个 ordinal、2 条 revlog。
- 首次导入必须 `created=2, conflicts=0, histories=2`；重复导入 `created=0` 且不重复历史。
- 导出再导入 Anki 后，两张卡的模板方向、due 和历史均可核对。

## P1-04 Anki 跨日学习和掩埋/暂停排程被错误转换

### 触发条件与证据

- `queue=1` 的学习卡 `due` 是 Unix 秒；`queue=3` 的跨日学习/重学卡 `due` 是 collection day number。
- `app/anki_exchange.py:348-358` 将 `queue=3` 与 queue=1 放在同一分支；当 due 小于 10 亿时直接设为“导入时刻”，使未来跨日卡立刻到期。
- 新卡被 bury/suspend 后通常是 `type=0, queue=-2/-1`；当前只有 `type=0 AND queue=0` 才识别为新卡，负 queue 会落到 review 分支。
- 导出 `due_at=None` 的新卡时，`app/anki_exchange.py:500-514` 直接写 `queue=0`，忽略 `card.buried`，导致 Anki 中自动解除掩埋。

### 影响

- 卡片会提前出现、从新卡变成复习卡，或者解除用户明确设置的“不想学”。
- reps/interval 看似保留，但学习队列语义已改变，属于学习进度损坏。

### 最小修复

- 按 Anki `type + queue + due + odue + collection creation/day cutoff` 建立显式解码/编码矩阵。
- 分别处理 new、learning timestamp、day-learning、review、preview/filtered、suspended 和 buried。
- 不认识的 queue/type 组合拒绝并报告，不能猜测为 review。

### 验收标准

- 固定时间 fixture 覆盖 queue `0 / 1 / 2 / 3 / -1 / -2 / 4` 和 filtered `odue/odid`。
- `queue=3` 的未来日期在导入后仍为同一天，而不是导入时刻。
- `type=0, queue=-2` 导入后仍是 `state=new, due_at=None, buried=True`；反向导出后 queue 仍为 `-2`。

## P1-05 Anki 导出会静默丢失同毫秒复习历史

### 触发条件与证据

- Anki `revlog.id` 是全集合主键。
- `app/anki_exchange.py:524-565` 的 `used_ids` 每处理一张卡就重建；两张卡的本地 `ReviewLog.reviewed_at` 相同会产生相同毫秒 ID。
- `app/anki_exchange.py:689-692` 使用 `INSERT OR IGNORE`，后写入的冲突历史被静默吞掉。
- 批量评分或时间精度截断时，两张卡同毫秒并非异常输入。

### 影响

- 导出的 `.apkg` 可正常打开，但 revlog 数量少于站内，用户无法从界面发现历史已丢。
- 后续再次互相导入时，统计和排程重建都可能继续漂移。

### 最小修复

- 在整个 export collection 范围统一分配唯一、稳定的 revlog ID。
- 冲突时按稳定排序递增毫秒或基于本地日志 ID 派生；重复导出同一数据应得到相同映射。
- 移除 `OR IGNORE`，任何未预期主键冲突都应让导出失败并返回可诊断错误。

### 验收标准

- 两张卡各有一条完全相同 `reviewed_at` 的日志；解包后 `COUNT(revlog)=2`。
- 加入导入历史与本地历史混合冲突测试。
- 重复导出时 card/revlog ID 稳定，且所有历史条数与来源一致。

## P1-06 撤回评分可覆盖较新的 Anki 导入进度

### 触发条件与证据

- 页面只在最近 15 分钟有 ReviewLog 时显示撤回：`app/routes/card_routes.py:1454-1461`。
- 真正的 undo API `app/routes/card_routes.py:1626-1660` 没有检查 15 分钟，也没有卡 revision、行锁或最新 AnkiReviewLog 检查。
- 如果用户先站内评分、再导入较新的 Anki 排程、最后调用 undo，接口会把卡恢复成站内评分前的旧快照。

### 影响

- 刚导入的 due、reps、lapses、learning state 和 FSRS 状态会被旧快照覆盖。
- 多标签并发 undo/review 也可能使日志与卡片状态不一致。

### 最小修复

- 在一个事务中锁定目标 ReviewLog 和 Card，强制 15 分钟窗口。
- ReviewLog 保存评分后的 revision，undo 只允许当前 card revision 恰好对应该次评分。
- 若最新 `AnkiReviewLog` 或任何后续评分晚于目标日志，返回 409，不改卡、不删日志。
- undo 本身增加幂等 action ID 或原子删除条件，防止双撤回。

### 验收标准

- 超过 15 分钟为 404/409 且数据不变。
- “站内评分 → 导入较新 Anki → undo”必须拒绝，导入后的进度保持不变。
- 两个并发 undo 只有一个成功；undo 与新评分并发时不会丢日志或倒退 revision。

## P1-07 评分幂等与乐观锁是可选项

### 触发条件与证据

- `app/schemas.py:62-75` 将 `action_id` 默认为空、`expected_revision` 设为可空。
- single route 只有 `action_id` 非空时才要求 revision/写 `ReviewRequest`（`card_routes.py:1715-1749`）；batch 同样如此（`1884-1935`）。
- 当前网页会正确发送这两个字段，但旧客户端、脚本或缺字段的网络重试仍能用 `{rating: "good"}` 连续应用两次。

### 影响

- 同一次用户动作写入两条 ReviewLog，`reps` 增加两次，并把 FSRS 排程推进两次。
- 数据表已有幂等机制，但 API contract 没有强制，保护可被无意绕过。

### 最小修复

- 真实 single/batch 评分强制非空、格式合法的 `action_id` 和非空 `expected_revision`。
- 如必须兼容旧客户端，单独提供短期版本化兼容期并记录告警；不要让新接口长期静默降级为非幂等。

### 验收标准

- 缺少任一字段返回 400，不写 ReviewLog、不改变 card。
- 同一 action 重试返回幂等成功，日志和 reps 只增加一次。
- 不同 action 使用旧 revision 返回 409；并发测试只有一个请求修改卡片。

## P1-08 SQLite 批量评分在写锁内重复全量统计

### 触发条件与证据

- SQLite 下配额缓存被明确禁用（`app/api_support.py:244-246`）。
- `_user_storage_bytes` 每次会扫描语料、章节、词、卡片、查词和两类复习日志（`176-235`）。
- batch 评分先获取 `BEGIN IMMEDIATE` 写锁，再对最多 500 项逐条调用 `_require_storage_space`（`card_routes.py:1851-1865,1954-1958`）。

### 影响

- 一个 500 项批次可在全库写锁内执行约 500 轮多表聚合；用户数据越多越慢。
- 期间所有其他写请求可能超过 5 秒 busy timeout，表现为数据库繁忙或学习进度保存失败。
- 生产当前正使用 SQLite，因此不是仅理论上的扩展问题。

### 最小修复

- 进入逐项评分前汇总整批 ReviewLog 的预计新增字节，只执行一次配额检查。
- 保持每项 savepoint/错误隔离，但不要在循环内重复全量扫描。
- 更长期可在同一 SQLite 事务/连接维护精确计数；不要用独立写连接制造锁竞争。

### 验收标准

- 500 项 batch 中 `_user_storage_bytes` 最多调用 1 次。
- 接近 50 MiB 的测试用户提交大批次时，另一写请求在 busy timeout 内完成或得到可安全重试的明确响应。
- 批次部分失败时，配额与实际已写日志一致。

## P1-09 README 宣称的 PostgreSQL 路径会升级/运行失败

### 已确认事实

- README 把 Docker + PostgreSQL 列为长期自部署推荐路径。
- `app/db.py:646-659,738-771` 的三个旧库迁移使用 `BOOLEAN NOT NULL DEFAULT 0`；PostgreSQL 应使用 Boolean `FALSE`，否则旧表升级可能失败并阻止服务启动。
- `app/routes/dashboard_routes.py:188-195` 调用 SQLite 专属 `date(timestamp, '+N hours')`；PostgreSQL dashboard 会报函数不存在。
- 普通查词允许 200 字符，但 `LookupCache.query` 是 `VARCHAR(80)`；PostgreSQL 对 81–200 字符会报 DataError，SQLite 不执行长度约束。
- `tests/conftest.py` 和 CI 都只使用 SQLite，没有 PostgreSQL service。

### 影响

- 新 PostgreSQL 库的部分流程可能运行，但旧库升级或 dashboard/长短语查词会 500。
- CI 继续全绿也无法发现 README 推荐部署路径已经损坏。

### 最小修复

- 只新增迁移：Boolean default 使用 `FALSE`；不要修改已经发布的迁移记录。
- dashboard 改为方言无关的站点日界范围/表达式，并处理 DST 配置。
- LookupCache 使用能容纳业务上限的字段，或用摘要主键 + 原始 query。
- CI 增加真实 PostgreSQL，覆盖全新建库和代表性旧库逐版本升级。
- 增加 migration advisory lock/单进程迁移，避免多实例同时启动竞争。

### 验收标准

- PostgreSQL 旧库可以升级、重复执行和故障重试，用户/卡片/review 计数不变。
- PostgreSQL 下 dashboard、80/81/200 字符查词、注册、评分、Anki 核心 smoke 全通过。
- 两实例并发 init 只执行一次迁移，均能正常启动。

## P1-10 匿名普通 API 请求体可造成资源耗尽

### 触发条件与证据

- `app/main.py:57-99` 给所有非上传 API 设置统一 48 MiB 上限。
- 绝大多数认证/查词 schema 只有数百至数千字符；最大普通业务正文也只有 1,000,000 字符，不需要 48 MiB。
- 有 `Content-Length <= 48 MiB` 时不包装 receive；无 Content-Length 虽累计字节，但没有墙钟超时。
- FastAPI/Pydantic 在进入路由鉴权和业务限流前读取/解析 body。非浏览器客户端可以自己设置合法 Host/Origin，因此 CSRF 不是 DoS 防线。
- systemd 只有 2 GiB MemoryMax，Uvicorn 没有 concurrency limit。

### 影响

- 未登录攻击者可并发发送约 48 MiB JSON/无效 body，放大内存和解析成本。
- 慢速分块请求可长期占用连接/线程，造成 OOM 重启或正常请求排队。

### 最小修复

- 普通 JSON 全局上限降到 1–2 MiB，认证端点可设为更小；真正上传继续使用路由的专用流式上限。
- 无论 Content-Length 是否存在，都统一累计实际读取字节并施加总墙钟超时；伪小 Content-Length 也必须按实际字节拒绝。
- Caddy 设置 request body/读取超时，Uvicorn 增加合理的 `--limit-concurrency`。
- 观察真实最大请求后再调上限，不把“可配置很大”当作兼容性。

### 验收标准

- 有/无 Content-Length、声明偏小、超限 JSON、慢速分块都在路由执行前得到 413/408 类响应。
- 并发压力下内存保持在预算内，正常 `/livez` 和登录请求仍可响应。
- 上传 APKG/文件路径不受普通 JSON 限额误伤，仍由各自大小和 30 秒超时控制。

## 修复顺序与数据保护原则

建议严格按以下顺序实施：

1. **先修部署对密钥的删除风险**，否则刚配置的 R2 会被下一次发布删掉；
2. **再建立并验证备份恢复**，后续所有 schema/Anki 修复才有可靠回滚点；
3. **为 P1-03 至 P1-07 先补失败用例**，然后做最小代码和版本化迁移；
4. **修 SQLite batch、PostgreSQL CI 和 API body 边界**；
5. 每次只部署一个已测试、已提交的确定版本，部署后核对 revision 和数据计数。

任何修复都应遵守：

- 不删除、覆盖或批量重写现有用户卡片和 review；
