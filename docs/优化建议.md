# VocabTool 项目审查与优化建议

> 审查日期：2026-08-13
> 审查基线：`main` / `a1eac13`
> 本文件只记录审查结论和建议；审查阶段未修改业务代码、数据库或服务器数据。
> 会造成数据丢失、学习进度错误或生产不可恢复的问题，另见 [亟需修复.md](./亟需修复.md)。

## 一、结论摘要

- 未发现已经确认的 P0：没有发现可直接利用的远程代码执行、跨用户数据读取、明文密钥入库或认证绕过。
- 现有基础防护明显好于一般原型项目：密码与会话处理、用户数据隔离、CSRF/Host 校验、上传体积限制、PDF 隔离、评分事务、systemd 沙箱和 CI 都已有实质性实现。
- 当前最大风险不是“缺少更多功能”，而是以下四条链路没有被端到端证明：
  1. Anki 双向交换能否在所有队列/模板下完整保留卡片和学习进度；
  2. 生产数据库能否按计划备份、异地保存并实际恢复；
  3. 部署失败后能否保证线上仍是一个可追溯、可回滚的完整版本；
  4. README 宣称的 PostgreSQL 路径能否从旧库升级并正常运行。
- `259` 个 pytest 当前全部通过，但关键风险恰好位于现有用例没有覆盖的边界：Anki 多模板、跨日学习队列、跨卡同毫秒 revlog、导入与撤回交错、PostgreSQL 旧库升级和并发请求体。

## 三、现有做得好的安全与稳定性控制

### 3.1 认证与数据隔离

- 密码使用 PBKDF2-SHA256、60 万次迭代，登录比较使用恒定时间逻辑并有 dummy hash。
- Session 使用高熵随机令牌，数据库只保存令牌摘要；Cookie 为 HttpOnly、SameSite=Lax，生产开启 Secure。
- 登录限流、会话过期、每用户最多 10 个会话以及重置密码后撤销会话均已实现。
- 核心卡片、语料、词库、历史和 Anki 操作普遍带 `user_id` 条件；本次未发现可确认的跨用户直接对象引用漏洞。
- 密钥从环境变量读取；本次未发现仓库内的真实密钥或把 Key/验证码写入日志的路径。

### 3.2 Web 与上传边界

- 已启用 TrustedHost、同源 Origin/Fetch-Site 检查、CSP、HSTS、nosniff、frame 限制和 no-store。
- 上传正文按实际读取字节数封顶并有 30 秒超时；gzip 解压、ZIP 成员数和实际解压总量也有上限。
- ZIP 路径经过规范化，避免路径穿越；APKG SQLite 以只读、immutable、`query_only`、`trusted_schema=OFF` 打开。
- PDF 使用单独进程，有 CPU/内存/墙钟限制和强制终止；重型导入有全局并发槽。
- 前端输出和 Anki 导出路径已做 HTML 转义；本次未发现可确认的 XSS、SSRF、命令注入或任意路径写入。

### 3.3 学习状态与运行环境

- SQLite 开启外键、5 秒 busy timeout、WAL 和 `synchronous=NORMAL`。
- 正常评分路径已有 SQLite 写锁、PostgreSQL 行锁、revision CAS、action ID 幂等和批量 savepoint。
- Anki 导入有上传、集合、卡数、历史条数上限，失败会整体回滚；较新的本地站内进度已有保护逻辑。
- TTS 有文本长度、20 秒网络超时、全局并发、同文本锁、原子落盘和 512 MiB 缓存上限。
- 加固 systemd unit 有 2 GiB 内存限制、任务数限制、`NoNewPrivileges`、只读系统和 namespace/设备/内核限制。
- CI 已包含 gitleaks、pip-audit、Ruff、compileall、Python 3.11/3.12 测试和 JavaScript 语法检查。

## 五、P2：安全性优化

### 5.1 验证码计数、邮件限流和账号枚举

**现状**

- 验证码错误次数是“先读 `attempts`、Python 加一、再提交”，并发请求可能丢更新；注册提交接口本身没有低阈值尝试限流。
- 未注册邮箱请求密码重置时，每次都会发送“该邮箱未注册”通知，却绕过已注册邮箱才有的 60 秒/每小时限制。
- 已注册邮箱第二次请求会很快返回，未注册邮箱仍等待邮件供应商，形成响应时延侧信道。
- 邮件发送发生在限流状态落库前，并发请求可能同时通过检查并发送多封。

**建议**

- 以“用途 + 归一化邮箱摘要 + 来源”为键，在外发前原子预占发送窗口；不存在和存在账号走相同的节流与响应路径。
- 不必向不存在的邮箱发送通知；统一返回内容即可。若保留通知，必须使用相同的每邮箱节流。
- 验证失败次数和验证码消费改成条件 `UPDATE` 或行锁，保证同一码最多消费一次、最多 5 次错误机会。
- 给 `/register` 增加低阈值来源/邮箱摘要限流；并发测试应证明最终计数准确且不会超过尝试上限。

### 5.2 XML 实体过滤可被 UTF-16 绕过

**证据**

- `app/file_import.py:57-60` 只在原始 bytes 中搜索 ASCII `<!DOCTYPE` / `<!ENTITY`。
- UTF-16 XML 的字节序列不包含这两个 ASCII 子串；本次最小样例已确认标准库 `ElementTree` 会继续展开其中的内部实体。

**建议**

- 所有不可信 XML 统一改用禁止 DTD/entity 的安全解析器（例如 `defusedxml.ElementTree`），不要依靠字节子串。
- 测试 UTF-8、UTF-16LE、UTF-16BE、大小写/空白变体和实体链。
- 现有 ZIP/解压上限能降低影响，但不能作为 XML 解析安全边界。

### 5.3 复杂文件解析隔离不一致

**现状**

- PDF 已有进程级 CPU/内存/墙钟隔离。
- APKG、EPUB、DOCX、XLS/XLSX 和用户 SQLite 仍在 Web 进程线程池中解析；APKG 的 `quick_check` 和 SQL 查询没有 progress handler/查询步数限制。

**建议**

- TXT/Markdown/CSV 等简单格式可保留进程内解析；复杂归档、数据库和 Office 格式复用 PDF 的子进程沙箱。
- 为 SQLite 增加 `progress_handler`、page count/page size 和墙钟上限；超时后必须确认子进程已退出。
- 使用畸形 schema、无索引 revlog、大 sharedStrings/样式表做资源上限测试。

### 5.4 `/healthz` 不应成为数据库连接放大器

**现状**

- 公网 `/healthz` 无认证/限流；PostgreSQL 模式使用 `NullPool`，每个请求建立真实数据库连接。
- 这样避免占用业务连接池，但高并发公网请求会放大连接握手、数据库连接数和线程消耗。

**建议**

- 拆分公网轻量 `/livez` 与仅反代/内网使用的 `/readyz`。
- readiness 使用容量极小的专用池或 1–5 秒缓存加 singleflight；反代层限制频率。
- 外部监控检查 HTTPS/Caddy；应用 readiness 只检查本应用必须依赖的数据库和 schema/revision。

### 5.5 游客资源预算与共享缓存隐私

- 游客 20 次查词额度是普通读改写；并发可能丢计数或首次插入冲突 500。复用 `GuestAiQuota` 的条件更新 + 插入冲突重试即可。
- 游客 TTS 只有来源每小时上限，没有全站 cache-miss 预算；分布式来源可长期占用 6 个生成槽。建议未登录只允许 cache hit，或增加全站每日生成预算。
- 普通查词允许任意 200 字符文本，却将 AI 结果存入全站共享 `LookupCache`。精确知道某个独特短语的人可通过 `lookup_source` 推断此前是否查过；建议只全局缓存规范化单词/短语，任意句子使用用户级短期缓存或不缓存，并明确保存期限。

### 5.6 供应链门禁

- 直接依赖已固定版本且当前审计无已知漏洞，这是良好基础。
- 传递依赖未完整锁定/带哈希，Docker 基础镜像和 GitHub Actions 使用可变 tag；gitleaks job 的 write 权限也应按实际需要收窄。
- 建议生成带哈希的完整锁文件、输出 SBOM、固定容器 digest 和 Actions 完整 commit SHA，并用 Dependabot/Renovate 更新。

## 六、P2：数据一致性与稳定性优化

### 6.1 明确定义 Anki 与 FSRS 的交换语义

- 导入较新 Anki 排程时会无条件将 `card.fsrs_state = None`；下一次站内评分只能用 interval/ease 粗略重建 FSRS，不能完整保留 Anki FSRS memory state。
- 需要明确产品承诺：
  - 若站内已有较新 FSRS，始终保留站内状态；
  - 若以 Anki 为准，使用可验证的 revlog 重放/映射；
  - 如果只能近似迁移，应在导入预览和结果中明确提示，而不是宣称完全无损。
- 测试不能只比 `due/reps/interval`，还要比较导入后四个评分选项的下一次到期时间。

### 6.2 存储配额应与业务事务一致

- PostgreSQL 的配额预占使用独立 Session 先提交；随后 Anki 导入/评分事务失败时不会补偿，缓存会虚增。
- 删除也不立即减缓存；当前“超限时重算”能自愈，但正常写在 60 秒内可能读到虚高值。
- 建议在业务提交成功后原子增加，失败时标记 dirty/补偿；删除后立即释放或标记过期。
- 回归测试覆盖导入中途异常、重复幂等导入、批量删除和并发预占。

### 6.3 数据库迁移并发与方言

- migration runner 和版本记录是两个事务，且没有跨进程锁；多实例同时启动可能双跑迁移或竞争版本主键。
- PostgreSQL 使用 advisory lock；SQLite 使用独占迁移锁，或者明确由部署阶段的单一迁移进程执行。
- 已发布迁移不得修改；只新增版本化修复迁移，并用旧库快照验证升级、重复执行、runner 成功后记录失败等场景。
- PostgreSQL Boolean 常量应使用 `FALSE/TRUE`；官方文档推荐 SQL 标准关键字：[PostgreSQL Boolean Type](https://www.postgresql.org/docs/current/datatype-boolean.html)。

### 6.4 PostgreSQL 的其他已确认差异

- `dashboard_routes.py:188-195` 使用 SQLite 专属 `date(timestamp, '+N hours')`。
- `LookupCache.query` 是 `VARCHAR(80)`，但普通查词允许 200 字符；PostgreSQL 会拒绝 81–200 字符，SQLite 测试不会暴露。
- CI/fixture 全部固定 SQLite，无法守护 README 的 Docker + PostgreSQL 推荐路径。
- 建议增加 PostgreSQL service job，至少覆盖注册、查词边界、卡片生成、评分、dashboard、Anki、旧库升级和迁移重复执行。

### 6.5 后台任务与多 worker 扩展门槛

- AI 文章任务、状态和用户互斥都只在进程内；重启会丢任务状态，多 worker 会允许重复生成。
- 存储锁、重型导入槽、制卡锁也都是进程内保护。目前 systemd 单 worker 下成立，但必须在配置中明确这一约束。
- 若要多 worker，先将任务状态/互斥落到数据库或队列；不要仅增加 worker 数。
- 最小持久化状态应有 `pending/running/succeeded/failed/interrupted` 和 `(user, day, source)` 唯一约束；启动时将遗留 running 标为 interrupted。

### 6.6 AI 制卡重试分类

- `app/ai.py` 对所有异常先做 2 次网络尝试，整批失败又可重新入队 20 轮，口语卡 30 轮。
- 401/403/参数/余额/429/本地“AI 请求繁忙”等永久或应快速失败的错误也会被放大，最多形成 40/60 次尝试并重复占用每日额度。
- 统一 `is_retryable_error`：只对连接错误、超时、明确的 5xx 重试一次；认证、参数、余额、限额和本地繁忙立即停止。
- 网络失败计数与“返回格式缺词”的修复计数分开；测试供应商 401、429、503、超时和本地槽满。

### 6.7 Dashboard 查询成本

- `load_only` 漏了 `Card.fsrs_state`，随后预测逐卡读取，形成每卡一次懒加载 N+1。
- 近 30 天 review log 和语料词频部分路径一次性加载，数据接近配额上限时延迟/内存线性增长。
- 先把 `fsrs_state` 加入同一查询并添加“查询次数”回归；再按真实基准决定是否 SQL 聚合/分页，不需要预先引入缓存系统。

## 七、P2/P3：部署、备份与可运维性

### 7.1 维护脚本必须 fail closed

- `auto-maintenance.sh` 对 `BACKUP_FAIL/R2_FAIL/HEALTH_FAIL/PIP_CHECK_FAIL` 只写日志，脚本通常仍以 0 退出，也没有触发告警。
- 本地备份失败后仍会运行 R2 同步；`r2-backup.sh` 上传后按 7 天删除旧对象，连续失败可能逐步删除最后的有效异地备份。
- 所有产物先写 `.part`，校验后原子改名；任一步失败都跳过上传/清理、非零退出并告警。加 `flock` 防止任务重叠。
- 远端清理只能发生在“本轮生成、上传并校验成功”之后，而且始终保留最低数量的已验证恢复点。

### 7.2 备份要按当前活动数据库执行

- `backup-native.sh` 固定尝试 `pg_dump --dbname=vocabflow`，不读取实际 `DATABASE_URL`；PostgreSQL 失败后只要服务器还残留 SQLite 文件，就可能把整次备份判为成功。
- 先识别当前活动方言，只备份该数据源；活动数据库备份失败必须失败退出。
- R2 当前直接上传 `.dump/.db/.tar.gz`，与 `docs/API调用设计.md` 中“加密后的异地备份”不一致。使用 age 或 rclone crypt，解密密钥离线保存；R2 凭据移出应用目录并使用最小 bucket 权限。
- 保留策略不要只有滚动 7 天；至少定义日/周/月恢复点、RPO、RTO 和定期恢复演练。

### 7.3 发布版本与健康检查

- 发布后写入 `REVISION`，readiness 返回预期 schema/revision；服务器应能明确对应某个 Git SHA。
- `curl` 增加 `--connect-timeout`/`--max-time`，不要让维护脚本无限挂起。
- 仓库同时有弱化的 `vocabflow.service` 和加固的 `deploy/vocabflow@.service`；删除旧 unit 或明确标记为废弃，避免误装。
- `deploy.sh` 排除整个 `data/`，跟踪的 NGSL/内置词表更新不会随原生部署发布。把只读资源与运行时数据库/TTS/temp 分目录，分别制定同步规则。

### 7.4 Docker 路径

- Web 已使用非 root 用户，这是好的。
- 可补 `read_only`、`tmpfs`、`cap_drop: ALL`、`no-new-privileges`、PID/内存上限；数据库和 Web 使用独立最小权限网络/卷。
- CI 增加 Docker build 和容器启动 smoke，再考虑镜像扫描；不要让 Docker 文档路径长期脱离真实测试。

## 八、P3：前端与 PWA

### 8.1 Service Worker 目前不能控制应用页面

- 前端注册 `/static/sw.js`；默认 scope 只能是 `/static/`，不能控制 `/`，所以导航离线兜底实际上不会生效。
- 从根路径 `/sw.js` 提供 worker 并设 scope `/`；`cache.put` 要纳入 fetch event promise 生命周期。
- CI 增加真实浏览器离线 E2E，验证 API/用户数据绝不缓存、静态壳可离线打开、升级后旧缓存被清理。

### 8.2 CSP 与主题启动脚本冲突

- CSP 为 `script-src 'self'`，但 landing/login 的 `<head>` 含内联主题脚本；标准浏览器会拦截内联脚本，造成首屏主题闪烁和控制台违规。
- 保留严格 CSP，把首屏主题 bootstrap 移到外部静态文件或使用 nonce/hash；不要用 `'unsafe-inline'` 解决。

### 8.3 明确的小问题

- 登录页 manifest 写成 `/static/manifest.webmanifest`，实际路由是 `/manifest.webmanifest`。
- CI 没有运行已经存在的 3 个 JavaScript 行为测试，也没有语法检查 `theme-sync.js`/`sw.js`；应纳入门禁。
- 带内容 hash 参数的静态资源仍统一 `no-cache`。可让真正版本化资源使用长期 `immutable`，worker 和无版本资源继续 no-cache。
