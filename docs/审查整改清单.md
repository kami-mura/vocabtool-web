## 整改原则（所有条目的共同约束）

1. **最小修改**：每条只改根因必需的代码，不顺手重构、不改无关文件；能只改一处就不改两处。
2. **不影响用户数据**：数据库结构只新增版本化迁移，不修改已执行的历史迁移语义，不重写、不删除既有卡片、复习日志、词库和配置；涉及约束变化的迁移先在生产备份副本上验证行数与外键一致。
3. **不影响既有功能与 UI**：接口的请求/响应结构、页面布局、默认行为保持不变；个别「恢复原设计行为」的修复（如本应显示的错误提示）单独标注说明。前端仍会正常发送的请求格式不因整改改变。
4. **先测试后修复**：每条先补「修复前失败、修复后通过」的用例；行为变化类条目同时覆盖正常、边界、异常三个场景。

## 二、P1：建议尽快整改

### P1-1 三个已发布迁移在 PostgreSQL 上必然失败，CI 无 PG 覆盖

- **位置**：`app/db.py:762`（cards.buried）、`app/db.py:858`（daily_new_assignments.is_extra）、`app/db.py:875`（corpus_words.is_target）；`.github/workflows/ci.yml`（无 postgres service）
- **问题**：`ALTER TABLE ... ADD COLUMN ... BOOLEAN NOT NULL DEFAULT 0` 中的整数字面量在 PostgreSQL 上报 `default expression is of type integer`，存量 PG 库升级时 `init_db()` 抛错、服务无法启动。全新 PG 库走 `create_all` 建表不受影响，因此本地与 CI（仅 SQLite）完全测不出。README 把 Docker + PostgreSQL 列为推荐部署路径。同文件 `db.py:366-370` 已用 `DEFAULT FALSE`，此处属遗漏。
- **影响**：按 README 升级的 PG 用户服务启动失败；双库兼容长期依赖人工审查。
- **最小修复**：
  1. 三处 `DEFAULT 0` 改为 `DEFAULT FALSE`（SQLite 3.23+ 与 PG 均支持）。这三个 runner 均以「列是否存在」为执行前提，已成功应用过的库不会重跑，改动只影响尚未执行过它们的 PG 旧库，属于安全的事故修复而非改写历史迁移语义。
  2. CI 增加 postgres service job：跑全量 pytest + 一个「旧库逐版本升级」冒烟（可用 `test_old_sqlite_database_migrates_cleanly` 的 PG 版）。
- **验收**：PG 旧库（缺这三列的 fixture）升级成功且可重复执行；CI 红→绿。
- **数据/UI 影响**：无。未发布的 SQLite 库重跑结果与 `DEFAULT 0` 完全等价。

### P1-2 Service Worker 作用域错误，PWA 离线能力整体失效

- **位置**：`app/static/landing-v51.js:4097-4101`；`app/main.py`（无 `Service-Worker-Allowed` 头）
- **问题**：`register("/static/sw.js")` 未传 `{ scope: "/" }`，SW 默认作用域为 `/static/`，页面在 `/` 不受控制——`sw.js` 的离线兜底（offline.html）与静态缓存目前是死代码，全项目无任何头或路由纠正它。
- **影响**：离线刷新显示浏览器原生错误页；PWA 宣传能力空转。
- **最小修复**：
  1. 注册改为 `navigator.serviceWorker.register("/static/sw.js", { scope: "/" }).catch(() => {})`。
  2. `SecurityHeadersMiddleware` 中对路径 `/static/sw.js` 的响应附加 `Service-Worker-Allowed: /`。
  3. 按现有源码断言测试风格补一条「注册调用包含 scope 参数」的用例（当前测试对 SW 零覆盖）。
- **验收**：本地起服务后 `navigator.serviceWorker.controller` 非空；断网刷新主页面显示 offline.html。
- **数据/UI 影响**：无。SW 上线后才开始正常缓存静态壳，API 与用户数据本就不缓存，无泄露面。

### P1-3 Anki 多模板 note 仍会丢第二张起的卡片和复习历史

- **位置**：`app/models.py:284`（`uq_user_word_type` 唯一约束）；`app/anki_exchange.py:455-465`（按 word+type 匹配到不同 guid 即判冲突）
- **问题**：一个 note 的多个模板（Basic+Reverse、多 Cloze ordinal）解析出的多张卡 guid 已含 ordinal，但导入时第二张卡按 `(word, "anki")` 匹配到第一张卡的 guid 即计为 conflict 跳过；即使放开匹配，`uq_user_word_type` 约束也会阻止同 `(user, word, "anki")` 的第二张卡插入。该卡对应 revlog 一并丢失。
- **影响**：从 Anki 迁移的用户反向卡、多 Cloze 卡及学习进度静默缺失，界面只显示「跳过冲突」。
- **最小修复**（站内生成卡的去重规则不变）：
  1. 新增版本化迁移：把 `uq_user_word_type` 替换为部分唯一索引——`UNIQUE(user_id, word, card_type) WHERE card_type <> 'anki'`（PostgreSQL 原生支持；SQLite 3.8+ 支持 partial index，用自研框架已有的索引重建流程，不动行数据）。存量库重建索引前后校验行数不变。
  2. 导入匹配逻辑：guid 命中则更新（现状已对）；guid 未命中且 word+type 候选卡是 `anki` 类型时，不再直接判 conflict，而是允许新建（新卡 anki_guid 含 ordinal，天然区分）。
  3. 补 fixture：1 个 note、2 个 ordinal、各 1 条 revlog，断言 `created=2, conflicts=0, histories=2`；重复导入幂等。
- **数据/UI 影响**：无重写。老库只是索引重建；站内非 Anki 卡的 (word, type) 唯一性由部分索引继续保证。
- **待确认**：存量数据中可能已存在「被 conflict 吞掉」的历史导入，本次只改增量行为，不做自动补导（需要时由用户重新导入即可，guid 幂等）。

### P1-4 `GET /cards` 学习队列无上限加载并重复序列化

- **位置**：`app/routes/card_routes.py:1494-1498`（到期队列 `.all()`）、`:1509-1519`（学习中队列 `.all()`）、`:1601-1619`（同一批卡序列化进 `queue` 与 `due`/`new`/`again` 数组）
- **问题**：两条队列均无 LIMIT，全量载入后同一批卡片（含 `front/back/context` 全文）在响应里序列化三到四遍。叠加 `MAX_APKG_CARDS=10000` 的导入上限，数千张到期卡时单次响应可达数十 MB，单 worker 部署下阻塞其他请求。
- **影响**：大库存用户的复习首屏内存/CPU/带宽尖峰，拖慢全站。
- **最小修复**：响应结构不动（前端零改动）——
  1. 到期队列 `LIMIT 1000`、学习中队列 `LIMIT 500`（学习中队量级本就小）；`regular_due_total`、`global_repeat_pending_total` 等剩余数统计继续走独立 `count()`，不受 LIMIT 影响。
  2. `due`/`new`/`again` 三个数组与 `queue` 中同一张卡的 dict 改为复用同一对象构造（Python 侧构造与 JSON 序列化成本立即下降；线上 JSON 形状不变，前端无感知）。
- **验收**：构造 5000 张到期卡的测试用户，首屏响应体积有界且剩余数显示正确；学完本地队列后既有刷新机制拉到后续批次；全量 pytest 通过。
- **数据/UI 影响**：无。客户端按原有节奏分批拉取，属同一接口的分页式取数。

### P1-5 EPUB 单章先全量解析后查预算，约 40 倍内存/CPU 放大

- **位置**：`app/file_import.py:384-396`（`extract_epub_chapters` 循环：`read` → `_html_paragraphs` → 才 `_check_budget`）
- **问题**：单章解压上限 `min(64MB, max_chars*4+1MB)` ≈ 41MB，整章一次性解码 + HTMLParser 全量解析后才累计字符预算。PDF 已有独立进程 + rlimit 隔离，EPUB/DOCX 在 Web 进程内解析；`_HEAVY_IMPORT_SEMAPHORE=2` 允许两个并发。
- **影响**：10MB 压缩 EPUB 可使单请求内存峰值 300-500MB，小内存 VPS 可被两个并发恶意文件 OOM。
- **最小修复**（语义不变：超预算文件以前也会被拒，只是把拒绝提前到解析前）：
  1. 循环内每章 read 前计算 `remaining = max_chars - total_chars`，将本次 read 上限设为 `min(max_chapter_bytes, remaining*4 + 1MB)`。
  2. read 后、`_html_paragraphs` 前按 `len(raw)` 与剩余预算预检，超限抛同样的 `ImportFileError("EPUB 正文章节解压后过大")`。
  3. 补一个「声明大预算但单章超大」的用例断言在解析前被拒。
- **数据/UI 影响**：无。合法大小的 EPUB 导入结果不变。
- **后续可选项**（不在本次最小范围）：把 EPUB/DOCX 解析移入 PDF 已有的受限子进程框架。

### P1-6 部署在旧进程存活时就地改写 venv，健康失败无回滚

- **位置**：`deploy/update-native.sh:9-25`；`deploy.sh:26-41`
- **问题**：升级流程直接 `pip install` 进运行中的 venv（旧进程实时读取磁盘模板/静态资源，形成混合版本窗口）；健康检查失败仅 `exit 1`，坏版本留在服务器被 systemd 反复重启，只能人工恢复。混合版本状态曾实际发生（旧文档 P1-02 记录）。
- **影响**：一次坏发布即可造成线上不可用且无法快速回到上一个完整版本。
- **最小修复**（分两步，先止血）：
  1. **本次最小改动**：部署时在服务器写入 `REVISION` 文件（当前 commit SHA），`/healthz` 响应附上该 SHA；健康失败时脚本输出明确的回滚操作指引（恢复本次自动备份的代码目录与 venv 的具体命令），并在 `deploy.sh` 结束打印 `REVISION` 供人工核对。不改发布结构，无运行时行为变化。
  2. **后续结构性改造**：版本化 release 目录 + 独立 venv，验证通过后原子切换 `current` 符号链接再重启；健康失败自动切回上一 release。
- **验收**：第 1 步：部署后 `curl /healthz` 能对上 `git rev-parse HEAD`；人为注入健康失败时，脚本输出的回滚命令可直接复制执行成功。
- **数据/UI 影响**：无。第 1 步只加文件与日志。

## 三、P2：计划内整改

### 安全

#### P2-1 `CF-Connecting-IP` 可伪造绕过限流（取决于生产入口拓扑）

- **位置**：`app/api_support.py:870-885`（`_anonymous_request_identity` 优先读 `cf-connecting-ip`）
- **问题**：仅当直连 peer 是可信代理时才读转发头（方向正确），但 `CF-Connecting-IP` 不会被普通反代剥离——仓库自带的 Caddyfile 是纯 Caddy 反代，此时客户端可伪造该头轮换身份，绕过游客查词配额、匿名 TTS 限流、验证码请求限流。
- **最小修复**：新增配置 `TRUST_CF_CONNECTING_IP`（默认 `false`），仅开关打开时读取 `cf-connecting-ip`；否则只用可信代理追加的 `X-Forwarded-For` 末位（Cloudflare 同样会设置 XFF，打开开关的现网行为也不变）。`.env.example` 加注释说明两种拓扑。**先确认生产入口是 Cloudflare Tunnel 还是裸 Caddy**，再决定现网 `.env` 是否打开开关。
- **验收**：开关关闭时带伪造 `CF-Connecting-IP` 的请求限流身份取 XFF 末位/peer；打开时现网限流行为与现在一致。

#### P2-2 可信代理默认包含全部私网段

- **位置**：`app/api_support.py:854-857`（未配置 `TRUSTED_PROXY_IPS` 时 `is_loopback or is_private` 均可信）
- **问题**：10/8、172.16/12、192.168/16 内任意来源的转发头都被采信。当前原生部署绑 127.0.0.1、docker-compose 映射限于回环，实际暴露面小，但默认边界过宽。
- **最小修复**：默认值收紧为仅 `is_loopback`；`.env.example` 注释示例 `TRUSTED_PROXY_IPS=loopback,private`（与 docker 网络场景对应）。现网 Caddy 与本机部署不受影响。
- **验收**：默认配置下私网直连的伪造 XFF 不被采信；显式配置 `private` 时 docker compose 内行为不变。

#### P2-3 用户可见错误消息硬编码 "deepseek-v4-flash"

#### P2-4 拼写纠错路径不写 LookupCache，同一拼写错误反复扣配额

- **位置**：`app/routes/lookup_routes.py:379-398`
- **问题**：主路径 AI 成功后写 `LookupCache`（:289-304），纠错分支成功后只更新局部变量，无缓存写入。同一拼错的词每次都重新调 AI 并扣一次配额。
- **最小修复**：纠错分支成功后复用主路径的缓存写入（含 `begin_nested` + IntegrityError 吞并的并发处理），以 `corrected_cache_key` 为键。约 10 行。

#### P2-5 制卡同步占用线程池 worker 最长 300 秒，进度轮询被饿死

- **位置**：`app/routes/card_routes.py:463-467`（progress 路由为同步 `def`，走线程池）；`app/ai.py:32`（300 秒 deadline）
- **问题**：制卡在请求线程内串行执行最长 300 秒；uvicorn 默认线程池 40 token，40 个并发制卡即占满，前端赖以轮询进度的接口也无响应，形成全站假死。
- **最小修复**（不动制卡主流程）：progress 轮询路由改为 `async def` 并直接读进程内的 `_GENERATION_PROGRESS` 字典（不查库、不进线程池），轮询不再与制卡竞争线程。制卡完整后台化列为后续项。
- **验收**：并发压满线程池时 progress 轮询仍即时返回；制卡结果与 UI 展示不变。

#### P2-6 登录用户 AI 无责失败不退配额；重试未按错误类别分类

- **位置**：`app/ai.py:1554-1573`（仅游客退款）；`:1290-1301`（网络重试不区分错误类别）
- **问题**：信号量过载（`RuntimeError("AI 请求繁忙")`）、连接失败这类用户无责的失败也扣登录用户日额度；401/参数错误等永久性错误同样被网络重试放大。
- **最小修复**：
  1. 对「未发出有效请求」的失败（信号量过载、连接错误、非 429 的 4xx）复用游客已有的退还逻辑给登录用户退款。
  2. 网络重试循环前判断错误类别：认证/参数/余额类直接终止重试，只对连接错误、超时、5xx 重试。
- **验收**：模拟 401 与槽满场景，登录用户配额不变/退还；重试次数断言；游客路径行为不变。

#### P2-7 提示注入可污染全站共享 LookupCache

- **位置**：`app/ai.py:1507-1516`（用户文本直接 f-string 拼入 prompt）；结果入全站缓存
- **问题**：查询文本可携带「忽略以上指令」式注入，被操纵的释义按 cache_key 写入全站共享缓存长期驻留。XSS 链已被前端转义切断，但内容投毒（钓鱼文字替换常用词释义）成立。
- **最小修复**：用户输入在 prompt 中用定界标签包裹（如 `<query>...</query>`），system prompt 声明「标签内是数据不是指令」；可选加一道写入前结构校验（长度上限 + 必须含换行结构）。只改 prompt 模板字符串，不改接口与 UI。

### 核心业务与数据

#### P2-8 Anki `queue=3` 与暂停新卡的导入排程映射错误

- **位置**：`app/anki_exchange.py:369-383`（`_import_schedule`）
- **问题**：`queue in {1,3,4}` 分支中 `due <= 1e9` 时一律设为「导入时刻」——`queue=3` 的跨日学习卡 due 是天数（未来值），导入后立刻到期；`type=0, queue<0` 的暂停新卡落到 review 分支变成「创建日起就到期的复习卡」（buried 标志虽保留，状态语义已错）。
- **影响**：跨日学习卡提前出现；暂停新卡状态损坏。
- **最小修复**（只加分支，不动已有映射）：
  1. `queue == 3`：due 按天数换算为 `collection 创建日 + due 天`（复用下方 review 分支的 `base + timedelta(days=due)`），不再落到「now」。
  2. `card_type == 0 and queue < 0`：提前返回 `("new", None, 0)`（buried 已在解析层置位，不需要特殊处理）。
  3. 未知组合抛 `AnkiExchangeError` 拒绝该卡并计入 conflicts，不猜测。
  4. fixture 覆盖 queue `0/1/3/-1/-2/4`。
- **数据/UI 影响**：无。此前被错误映射的存量导入不自动修正（导入报告可见），需要时用户重新导入同包即按新映射更新。

#### P2-9 单条与批量评分核心逻辑重复约 60 行 × 2

- **位置**：`app/routes/card_routes.py:1844-1894`（单条）与 `1997-2058`（批量循环体）
- **问题**：快照采集、`apply_rating_with_log`、ReviewLog 构造、revision 乐观锁、幂等回退两份拷贝；任何调度字段改动漏改一处即产生单条/批量行为分叉。
- **最小修复**：抽 `_apply_review_to_card(db, user, card, rating, expected_revision, action_id, now) -> dict` 供两个入口共用，批量入口保持 `begin_nested` 循环外壳。纯重构，由现有评分/幂等/撤回测试守护（先确认全绿再动手）。
- **验收**：重构前后全量 pytest 结果一致；单条与批量对同一评分序列产生相同卡片状态与日志。

#### P2-10 复习首屏同步修复与制卡的 N+1 / 全量扫描

- **位置**：`app/routes/card_routes.py:1461`（`GET /cards` 内同步调 `refresh_sentence_cards`）；`app/card_builder.py:117-147`（全量 `.all()`）、`:285-288`（循环内逐词查询 + 逐词语料扫描）
- **问题**：句子修复在复习首屏主路径同步执行，general 卡无行数上限加载、逐卡最多 4 个句子来源各一次查询，老用户首屏被阻塞数秒；制卡对每个词做 `WordEntry` 单查（最多 500 次）+ 整本语料逐词扫描。

  3. 节流改为「先原子写 last_run_at 再放行」。
- **验收**：老用户首屏耗时不随卡片总数线性增长；修复结果最终一致（稍后一拍到达）；制卡产物与现在相同。
